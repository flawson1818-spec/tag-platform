1. Vision du produit (rappel)

TAG est une plateforme mondiale d'intercession chrétienne continue : une salle de prière est active quelque part dans le monde à chaque instant, 24h/24, 7j/7. Le programme est découpé en créneaux successifs (PrayerSlot), animés par un responsable humain ou, en son absence, par une IA Animatrice. L'IA anime et assiste, mais ne remplace jamais l'autorité pastorale sur les décisions sensibles.

Le dépôt suit un ensemble de 17 documents de spécification (docs/01 à docs/17) qui font autorité sur toute décision d'architecture ou de règle métier. Rien n'est censé être inventé en dehors de ce qu'ils décrivent.

2. Architecture technique

Frontend webReact 19 + Vite + react-router-dom (le document de roadmap recommandait Angular ; le dépôt existant avait déjà React — poursuivi par cohérence avec l'existant plutôt que réécrit)

Convention de code observée dans tout le dépôt : les services accèdent directement au client Supabase (pas de couche ORM), les contrôleurs restent minces (validation → appel service → retour), les DTO d'entrée sont en camelCase, les entités/réponses reflètent les colonnes de la base en snake_case.

3. Domaine Identity (Auth) Construit et vérifié

Fondation de toute l'application — premier domaine construit, conforme à l'ordre de génération imposé par les règles du projet.

3.1 Base de données

7 tables créées : users, roles, permissions, role_permissions, role_assignments, refresh_tokens, password_reset_tokens.

  • 8 rôles hiérarchiques : Visiteur → Nouveau Converti → Intercesseur → Modérateur → Responsable d'Équipe → Pasteur → Administrateur → Super Administrateur.
  • 17 permissions atomiques (ex. prayer_request.create, testimony.approve, user.manage) réparties sur 73 associations rôle-permission, reflétant exactement la matrice du document RBAC.
  • Mots de passe hachés en Argon2id ; politique : 12 caractères minimum, majuscule, minuscule, chiffre, caractère spécial.

3.2 Sécurité des sessions

  • Access token JWT, durée de vie 15 minutes.
  • Refresh token opaque (aléatoire, 48 octets), jamais stocké en clair — seul son empreinte SHA-256 est en base.
  • Rotation : chaque rafraîchissement invalide l'ancien token et en émet un nouveau.
  • Détection de réutilisation : si un refresh token déjà révoqué est présenté à nouveau (signe de vol), toute la famille de sessions de l'utilisateur est révoquée immédiatement.
  • Changement de mot de passe (réinitialisation) révoque automatiquement toutes les sessions actives.

3.3 RBAC — contrôle d'accès

Chaque route sensible vérifie une permission atomique (jamais un nom de rôle en dur) via un Guard NestJS dédié. Point clé validé par des tests réels :

Portée globale vs. scopée à une communauté. Une attribution de rôle globale (community_id = NULL) donne ses permissions partout. Une attribution scopée à une communauté précise ne donne ses permissions que dans cette communauté — vérifié en direct : un utilisateur promu Responsable d'Équipe uniquement sur une cellule ne peut pas agir sur une autre communauté (403 confirmé).

Anti-escalade : l'endpoint d'attribution de rôle plafonne volontairement à Pasteur — impossible d'attribuer Administrateur ou Super Administrateur par cette voie, conformément à la note du document RBAC.

4. Domaine Community Construit et vérifié

Deuxième domaine, dans l'ordre de génération imposé (Identity → Community → Prayer...).

4.1 Base de données

  • communities — hiérarchie via parent_id, types GROUP / TEAM / CELL / COUNTRY / CITY / CHURCH / MINISTRY.
  • community_members, posts, comments.
  • Nouvelle permission community.manage ajoutée (extension explicitement autorisée par le document RBAC, qui prévoit que la table des permissions grandisse avec chaque nouvelle fonctionnalité) — accordée à Responsable d'Équipe et au-dessus.

4.2 Règles de fonctionnement

  • Le créateur d'une communauté en devient automatiquement membre.
  • Seuls les membres d'une communauté peuvent y publier ou y commenter (vérifié : un non-membre reçoit 403, devient autorisé après ajout comme membre).
  • Créer une communauté à la racine (sans parent) exige une attribution globale de community.manage — créer une sous-communauté exige cette permission dans le contexte du parent.

4.3 Routes construites

POST/GET/PATCH/DELETE /communitiesCycle de vie de la communauté
POST/DELETE/GET /communities/:id/membersGestion des membres

Les listes (utilisateurs, communautés, membres, posts, commentaires) renvoient toutes une pagination cohérente { data, meta: { page, limit, total, totalPages } }.

5. Application web (React)

Amorce de l'interface, branchée sur la vraie API :

  • Pages Connexion et Inscription.
  • AuthContext : persistance de session (jetons en localStorage), restauration automatique au chargement, rafraîchissement silencieux si l'access token a expiré.
  • Tableau de bord protégé (redirection vers la connexion si non authentifié), affichant l'utilisateur courant.

Les deux maquettes visuelles statiques (salle de prière mondiale, écrans demandes/témoignages/calendrier/carte) existent séparément (prayer-room-preview.html, tag-screens-preview.html) mais ne sont pas encore branchées à l'API réelle.

6. Ce qui a été vérifié

  • Build, lint, typecheck propres sur api et web via Nx, à chaque étape.
  • Tests de bout en bout réels (pas de mocks) contre le vrai projet Supabase, via des appels HTTP directs au serveur en cours d'exécution :
    • Inscription → connexion → route protégée → 401 sans jeton.
    • Rotation du refresh token, puis réutilisation de l'ancien jeton → 401 + révocation de toute la session.
    • RBAC : 403 pour un Visiteur, 200 après promotion en rôle habilité.
    • Plafond anti-escalade sur l'attribution de rôle.
    • Communautés : création refusée/autorisée selon permission et portée, adhésion, publication bloquée puis débloquée après adhésion, isolation de portée entre deux communautés.
  • Toutes les données de test créées pendant ces vérifications ont été supprimées de la base après coup.

8. Ce qui reste à construire

Dans l'ordre de génération du projet (chaque domaine dépend des précédents) :

  1. Suivant Prayer — PrayerProgram / PrayerSlot, chronomètre serveur, transition automatique, salle mondiale continue, demandes de prière, témoignages.
  2. À faire Communication — notifications, e-mail réel, WhatsApp, publications multicanal.
  3. À faire Storage — fichiers, upload présigné.
  4. À faire Analytics — tableaux de bord, carte mondiale en temps réel.
  5. À faire Administration — journaux d'audit, sauvegardes.
  6. À faire Agents IA — Accueil, Intercession, Évangélisation, Modératrice, Communication, Analyse (dont « Le Veilleur » sur WhatsApp).
  7. À faire Application mobile Flutter, événements, gamification.
  8. À faire Déploiement Docker / production.
